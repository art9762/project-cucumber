# Project cucumber — план модуля анализа

Документ описывает, что строим поверх движка сбора (`search engine/`) и в каком
порядке. Решения зафиксированы; детали уточняются в начале каждой фазы.

## Замысел

Движок собирает идеи из публичных источников в Postgres. Поверх базы строится
**анализ**: идеи раскладываются деревом по категориям, оцениваются комплексным
коэффициентом, обогащаются веб-ресёрчем, и всё это видно через веб-панель с
умным поиском и поиском конкурентов.

```
источники ──► search engine ──► Postgres (items + raw_records + jobs)
                                      │  read-only
                                      ▼
                            ┌──── analysis ────┐
                            │ 1. классификация │  Haiku  → дерево категорий
                            │ 2. скоринг       │  Haiku→Sonnet/Opus → коэффициент → тир
                            │ 3. эмбеддинги    │  вектор на item (pgvector)
                            └──────────────────┘
                                      │
                        ┌─────────────┼─────────────┐
                        ▼             ▼             ▼
                   research       analysis API       ui
                 (веб-серч,      (дерево, тирлист,  (панель управления,
                 конкуренты      умный поиск,        умный поиск, подбор,
                 в вебе)         конкуренты)         поиск конкурентов)
```

## Зафиксированные решения

| # | Решение |
|---|---------|
| Доступ к данным | Analysis читает **ту же Postgres напрямую** (read-only к таблицам движка). Движок остаётся чистым сборщиком, связь через БД, а не HTTP. |
| Категории | **Гибрид**: seed-таксономия верхнего уровня (AI, инженерка, продукт, наука…), Haiku раскладывает items и предлагает новые подкатегории на ручное утверждение. |
| Скоринг | **Комплексный коэффициент по формуле**, основной вес — актуальность. Параметры: актуальность, сложность, новизна, зрелость, потенциал. Агрегат → тир S/A/B/C/D. |
| Семантика | **Эмбеддинги через pgvector** для поиска конкурентов (описал решение → нашёл похожее). Отдельная фаза, не на старте. |
| Размещение analysis | **Отдельный сервис** со своей FastAPI и своими таблицами. Общая Postgres со сборщиком. |
| Модели | Через **Trinity** (Anthropic-совместимый шлюз). Дёшево по объёму — Haiku 4.5, эскалация на Sonnet 4.6 / Opus 4.x по нужде. |

## Инфраструктура и эксплуатация

- **Хостинг:** один VPS (Нидерланды), всё крутится под **отдельным системным
  юзером** (не root), процессы изолированы.
- **Веб:** не просто витрина, а **полная панель управления** — запуск сбора и
  анализа, статусы джоб, просмотр/правка категорий и тиров, настройки.
- **Доступ:** сервис может быть расшарен друзьям → нужны **аккаунты**
  (аутентификация + роли). Вместе с безопасностью и аудитом — **отдельной фазой
  в конце**, не размазываем по ходу.
- **Процесс разработки:** пишем **swarm'ом из ruflo** (мульти-агентная
  оркестрация по фазам).

## Скоринг — параметры (черновик, уточним в Фазе 2)

| Параметр | Что значит | Источник |
|----------|------------|----------|
| Актуальность *(осн. вес)* | насколько тема горячая сейчас | модель + сигналы (даты, score источника) |
| Сложность | трудоёмкость реализации | модель |
| Новизна | насколько идея незаезженная | модель + близость к существующим (вектор) |
| Зрелость | насколько уже реализовано/есть продукт | модель + research |
| Потенциал | рынок / применимость | модель |

Коэффициент = взвешенная формула (веса настраиваемые, актуальность доминирует) →
порог → тир **S / A / B / C / D**. Формула и веса фиксируются в конфиге, чтобы
переоценивать без перезапуска кода.

## Фазы

> Каждая фаза = отдельный заход swarm'а: спека → реализация (TDD) → проверка.
> Двигаемся по одной, не забегаем вперёд.

### Фаза 0 — каркас `analysis/`
Модуль-сервис: структура пакета, **Trinity-клиент** (Anthropic SDK на
`base_url` Trinity, ключ из env), подключение к общей Postgres (read-only к
таблицам движка), свои таблицы под результаты анализа (Alembic), конфиг,
**инкрементальная обработка** (watermark по `fetched_at`/id items — берём только
новые), скелет FastAPI. Без логики анализа.

### Фаза 1 — классификация (дёшево)
Haiku раскладывает новые items по seed-дереву категорий, предлагает
подкатегории. Хранение дерева и привязок item→категория. Механизм ручного
утверждения новых веток.

### Фаза 2 — скоринг и тирлист
Присвоение параметров (актуальность, сложность, …), расчёт коэффициента по
формуле из конфига, тир S–D. Эскалация на Sonnet/Opus для важных/спорных идей.

### Фаза 3 — research (веб-серч)
Отдельный модуль `research/`: по выбранной идее — детальный веб-разбор и **поиск
конкурентов в вебе**. Результаты обогащают зрелость/потенциал в скоринге.

### Фаза 4 — эмбеддинги + analysis API
Векторизация items (pgvector). HTTP API: дерево категорий, тирлист с фильтрами,
**умный поиск**, **подбор по категориям**, **поиск конкурентов** (опиши решение
→ похожее из базы по вектору).

### Фаза 5 — UI / панель управления
Фронт (ui/ux pro max + motion) поверх analysis API: просмотр всех проектов,
умный поиск, подбор по категориям, поиск конкурентов, **управление** сбором и
анализом, настройки.

### Фаза 6 — аккаунты, безопасность, аудит
Аутентификация и роли (шаринг друзьям), хардненинг под отдельным юзером на VPS,
аудит безопасности. Финальная фаза — отдельно от продуктовой логики.

## Структура репо (целевая)

```
Project cucumber/
├── search engine/     сбор (есть, v1)
├── analysis/          классификация + скоринг + эмбеддинги + API   (Фазы 0–4)
├── research/          веб-серч и поиск конкурентов в вебе          (Фаза 3)
├── ui/                панель управления + поиск (бывш. test ui)    (Фаза 5)
└── docs/              общие планы и заметки
```
